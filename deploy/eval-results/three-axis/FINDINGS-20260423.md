# §6.2 Three-axis sweeps — first pass (2026-04-23)

First end-to-end run of the three §6.2 sub-sweeps defined in
`docs/sdk-aggregation-three-axis-design.md`. Cardinality=1000,
FREQ_HZ=10, SOAK_S=180, BYTES_WIN=20, N=1. Artifacts alongside:

- `6.2a-time-20260423.csv` — 4 rows, time axis
- `6.2b-label-20260423.csv` — 5 rows, label axis
- `6.2c-encoding-20260423.csv` — 8 rows, encoding axis

## TL;DR

- **Encoding axis (6.2c) is the cleanest finding.** `raw-buffer`
  uses ~3× the producer RSS of the sketch encodings and emits ~7×
  the wire bytes of any sketch. Sketch-to-sketch differences are
  within measurement noise at this cell.
- **Label axis (6.2b) shows a large memory win.** Projecting from
  keep-all down to `zone,rack` cuts producer RSS in half (67 →
  33 MiB) — attribute-set folding means fewer sketch instances
  held. CPU _increases_ under more aggressive projection because
  attribute filtering runs on every measure() call.
- **Time axis (6.2a) shows the expected bw drop with longer W,
  but the absolute numbers are undermined by a measurement-window
  bug — see caveat below.**

## Methodology caveat that bit us — `BYTES_WIN < W`

`producer_bytes_out_per_s` is measured by sampling `docker stats
NetIO` twice, separated by `BYTES_WIN` seconds, and dividing the
tx delta by that window. If the OTel SDK flushes every `W`
seconds and `BYTES_WIN < W`, there's a ~`1 − BYTES_WIN/W`
probability the sample window contains **zero** flushes — the
measurement then captures only container-level overhead traffic
(heartbeats, DNS, etc.), not the real OTLP payload.

This sweep used `BYTES_WIN=20s`, so:

| W | catches a flush? | bytes are |
|---|---|---|
| 1s | always (20 flushes in window) | **trustworthy** |
| 15s | usually (1-2 flushes) | approximately trustworthy |
| 60s | sometimes (0-1 flush) | **under-reported by ~3×** |
| 300s | almost never | **≈ 0, not real** |

So in `6.2a-time`:

| W | reported B/s | interpretation |
|---|---:|---|
| 1s | 584.9 | real |
| 15s | 52.2 | approximately real; the ~10× drop vs 1s is plausible |
| 60s | 5.85 | **floor noise** — true value is ≥ this but can't tell from this CSV |
| 300s | 0.00 | **floor noise** |

And in `6.2b-label` / `6.2c-encoding` (all at W=60s), the
absolute bytes column is uniformly under-counted. But **ratios
between rows at the same W are still valid** — they share the
same sample-window miss rate.

### Recommended fix for a v2 run

- Set `BYTES_WIN ≥ 2 × W` per cell so every sample catches at
  least one flush.
- For §6.2a specifically: either cap W at 60s (drop the 300s
  point) or set `SOAK_S=900, BYTES_WIN=600` for the 300s row.
- Expected rerun time at that budget: ≈90 min.

The sweep driver (`run-three-axis-sweep.sh`) should probably
auto-set `BYTES_WIN = max(W_values) × 2` as a floor — follow-up
item, not blocking this first-pass write-up.

## §6.2a — time axis (varies W, L=keep-all, agg=dd-full)

```
W     bytes_out_per_s  producer_cpu_cores  producer_rss_mib
1s    584.9             0.483               102.0
15s    52.2             0.218                94.0
60s     5.85*           0.250                68.5
300s    0.00*           0.241                42.9
```

`*` affected by BYTES_WIN caveat above.

**What's real even under the caveat**:

- Producer CPU drops from 0.48c at W=1s to ~0.24c at W=15s+
  and stays flat — the per-tick flush overhead dominates at
  W=1s, at which point there are 15-300× more flushes per
  second than at larger W. This matches expectations.
- Producer RSS trends _down_ with larger W, not up — surprising
  if you'd expect "longer window = more buffered state", but
  consistent with DDSketch's per-series summary being bounded
  in size regardless of how many observations fall in the
  window. The RSS drop is likely garbage collection between
  fewer flush cycles.

**What the caveat hides**:

- The "expected" paper claim was bw scaling roughly as 1/W —
  cannot be verified from this CSV for W ≥ 60s. Needs v2 run.

## §6.2b — label axis (varies L, W=60s, agg=dd-full)

```
L              bytes_out_per_s  cpu_cores  rss_mib
keep-all         5.85*           0.217      66.8
zone,rack,node   5.85*           0.526      58.6
zone,rack        5.85*           0.749      33.7
zone             5.85*           0.817      33.9
drop-all         5.85*           0.616      34.0
```

**What's real**:

- **RSS drops ~50% from keep-all to zone,rack** (66.8 → 33.7
  MiB). Projection folds attribute sets together, so the SDK
  holds fewer sketch instances. Drops plateau past 2 dims —
  fold-rate on this synthetic schema plateaus at that point.
- **CPU _increases_ with more aggressive projection** (0.22 →
  0.75c). Expected in principle — every measure() call runs
  through the AttributeFilter — but the magnitude is larger
  than expected. Worth a dedicated profile before paper
  submission.
- `drop-all` (L="-") has CPU between `zone` and `zone,rack`
  rather than at the extreme; likely the filter short-circuits
  faster. Lowest-priority follow-up.

**What the caveat hides**:

- The bandwidth column — all cells read identical within
  3 decimal places. Can't distinguish the folding benefit on
  bytes from this CSV. Needs v2 run with BYTES_WIN ≥ 120s.

## §6.2c — encoding axis (varies agg_type, W=60s, L=zone,rack)

```
agg           bytes_out_per_s  cpu_cores  rss_mib
raw-buffer     45.00*           0.329     108.7
dd-full         6.30*           0.867      33.0
dd-delta        6.30*           0.837      34.5
kll             6.30*           0.958      34.0
cms-full        6.30*           0.595      57.5
cms-delta       5.85*           0.634      86.4
hll-full        6.30*           0.625      37.6
hll-delta       5.85*           0.602      39.1
```

**Ratios between rows are meaningful** (same W → same under-count
factor on the bytes column):

- **raw-buffer / dd-full bytes ratio ≈ 7×.** Even with the
  under-count, raw-buffer clearly dominates — emits every
  measurement as its own data point vs. one summary per
  (attribute, window).
- **RSS tells a consistent story**:
  - `raw-buffer` holds 108 MiB — it literally buffers every
    `(ts, attr, value)` tuple for the whole 60s window.
  - `dd-full`, `kll`, `hll-full` all land ~33-38 MiB —
    constant-size-per-series sketches.
  - `cms-full` at 57 MiB is higher because CMS pre-allocates
    a fixed 2D counter array per attribute key.
  - `cms-delta` at 86 MiB is higher still — keeps the
    previous-tick snapshot alongside the current sketch for
    diff computation. Interesting signal: delta encoding is
    a memory / bandwidth tradeoff, not a free win.
- **CPU ordering**:
  - `kll` is most expensive (0.96c) — KLL's multi-level
    compaction runs on every insert.
  - `dd-full` / `dd-delta` next (~0.85c).
  - `cms*`, `hll*` cheapest on CPU (~0.60c) — simple hash-and-
    increment per insert.
  - `raw-buffer` is lowest (0.33c) — literally just appending
    to a slice.

**What the caveat hides**:

- The absolute `raw-buffer` bandwidth — really should be ≥ 135
  B/s (3× under-count) and possibly much higher under gzip
  compression anomalies. A v2 run at `BYTES_WIN=120s` will
  nail this down.
- `dd-delta` vs `dd-full` bytes differ by under 1% in this
  CSV — the delta story for DDSketch needs either higher
  cardinality or higher per-window change rate to see a
  meaningful diff. Worth a sensitivity sweep later.

## Non-obvious signals worth a second look

1. `6.2b` CPU _increases_ with label projection. If this
   reproduces under v2 methodology, AttributeFilter is on the
   hot path and probably needs optimization — this is a
   paper-negative finding to address pre-submission.
2. `cms-delta` memory overhead at 2× `cms-full`. Reviewers will
   ask about the delta mechanism memory cost; we should
   document this as a known tradeoff in the paper or look at
   in-place diff encoding.

1. **Add `BYTES_WIN ≥ 2×W` auto-floor to `run-three-axis-sweep.sh`**
