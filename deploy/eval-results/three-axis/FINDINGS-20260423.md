# SDK aggregation experiments

Measures what the SDK decision point costs under each of three
independent knobs. Design doc for the framework:
[`docs/sdk-aggregation-three-axis-design.md`](../../../docs/sdk-aggregation-three-axis-design.md).

## Experiment design

The SDK-side aggregation behaviour is fully specified by a triple:

```
(W,  L,             agg_type)
 time window        label projection        encoding
```

- `W` — `PeriodicReader.WithInterval`. How often the SDK flushes.
- `L` — `View.AttributeFilter`. Which label keys survive into the
  aggregator key (others are folded).
- `agg_type` — which `sdkmetric.Aggregation` is used (raw-buffer,
  DDSketch, KLL, CMS, HLL, ± delta encoding).

Three sub-experiments each vary one knob and hold the other two
fixed. Common setup: `N=1` agent, `cardinality=1000` distinct
attribute sets, fake-exporter firing at `freq_hz=10` per series
(two instruments — counter + gauge), `SOAK_S=180s` per cell,
`BYTES_WIN=20s` for the docker-stats tx-rate sample.

| Experiment (CSV) | What varies | What's held fixed | Cells |
|---|---|---|---|
| `6.2a-time-20260423.csv` | `W ∈ {1s, 15s, 60s, 300s}` | `L = keep-all`, `agg = dd-full` | 4 |
| `6.2b-label-20260423.csv` | `L ∈ {keep-all, zone+rack+node, zone+rack, zone, drop-all}` | `W = 60s`, `agg = dd-full` | 5 |
| `6.2c-encoding-20260423.csv` | `agg ∈ {raw-buffer, dd-full, dd-delta, kll, cms-full, cms-delta, hll-full, hll-delta}` | `W = 60s`, `L = zone,rack` | 8 |

Per cell the harness does: `docker compose down` → up with the
env → soak → `measure-baseline.py` reads the producer container's
CPU / RSS / tx-bytes from `docker stats` and the agent / gateway /
backend metrics from Prometheus. The `baseline` column in the
CSVs is a tag `w<W>-l<L>-a<agg>` so rows are trivially splittable
back onto the grid.

## Methodology caveat — `BYTES_WIN < W` under-reports bytes

`producer_bytes_out_per_s` is measured by sampling
`docker stats NetIO` twice separated by `BYTES_WIN` seconds and
dividing the tx delta by the gap. If the SDK flushes every `W`
and `BYTES_WIN < W`, there's a ~`1 − BYTES_WIN/W` probability the
sample contains **zero flushes** — the number then captures only
container-level overhead (heartbeats, DNS), not the real OTLP
payload. This run used `BYTES_WIN=20s`:

| W | catches a flush? | bytes are |
|---|---|---|
| 1s | always (20 flushes in window) | **trustworthy** |
| 15s | usually (1-2 flushes) | approximately trustworthy |
| 60s | sometimes (0-1 flush) | **under-reported ~3×** |
| 300s | almost never | **≈ noise floor, not real** |

**Within-sub-experiment ratios are still valid** when all rows
share the same `W` (label-axis and encoding-axis both at
`W=60s`) — same miss rate across rows. The time-axis table's
bytes column is the one that can't be read as-is.

Fix: set `BYTES_WIN ≥ 2×W`. For a v2 run at `W=60s` that adds
~100s per cell. Tracked as a driver follow-up.

## Results

### Encoding axis — `6.2c-encoding-20260423.csv`

```
agg           bytes_out_per_s  cpu_cores  rss_mib
raw-buffer     45.00*           0.329     108.7
dd-full         6.30*           0.867      33.0
dd-delta        6.30*           0.837      34.5
kll             6.30*           0.958      34.0
cms-full        6.30*           0.595      57.5
cms-delta       5.85*           0.634      86.4
hll-full        6.30*           0.625      37.6
hll-delta       5.85*           0.602      39.1
```

- `raw-buffer` bytes are **~7× any sketch** even under the
  BYTES_WIN caveat — it literally emits every measurement as
  its own data point instead of one summary per
  `(attribute, window)`.
- `raw-buffer` RSS is **3× the sketch encodings** — it buffers
  every `(ts, attr, value)` tuple for the whole `W=60s` before
  flushing.
- `cms-delta` RSS = 86 MiB vs `cms-full` = 57 MiB. **Delta
  encoding is a memory / bandwidth tradeoff, not a free win** —
  the aggregator keeps the previous-tick snapshot alongside the
  current sketch so it can compute the diff. Same pattern would
  apply to any sparse-state sketch with delta enabled.
- CPU ordering: `kll` highest (0.96c — multi-level compaction
  on every insert) > `dd-full`/`dd-delta` (~0.85c) >
  `cms-*`/`hll-*` (~0.60c — single hash-and-increment) >
  `raw-buffer` (0.33c — slice append).

### Label axis — `6.2b-label-20260423.csv`

```
L              bytes_out_per_s  cpu_cores  rss_mib
keep-all         5.85*           0.217      66.8
zone,rack,node   5.85*           0.526      58.6
zone,rack        5.85*           0.749      33.7
zone             5.85*           0.817      33.9
drop-all         5.85*           0.616      34.0
```

- **Projection folds attribute sets together** — going from
  keep-all to `zone,rack` cuts producer RSS roughly in half
  (66.8 → 33.7 MiB) as the SDK holds fewer sketch instances.
  The drop plateaus once the fold factor saturates on this
  synthetic schema (~2-dim is enough).
- **CPU _increases_ with more aggressive projection** (0.22 →
  0.82c, a ~4× climb). Every `measure()` call walks the
  `AttributeFilter` predicate — expected in principle, but the
  magnitude suggests the filter is on a hot path that deserves
  a profile.
- `drop-all` CPU (0.62c) sits below `zone` (0.82c) — likely
  short-circuit on empty-keep path; minor quirk.
- Bytes column is flat at 5.85 B/s because BYTES_WIN < W on
  every row (caveat). A v2 with proper window should show
  bytes dropping with the RSS.

### Time axis — `6.2a-time-20260423.csv`

```
W     bytes_out_per_s  cpu_cores  rss_mib
1s    584.9             0.483     102.0
15s    52.2             0.218      94.0
60s     5.85*           0.250      68.5
300s    0.00*           0.241      42.9
```

- **CPU drops ~2×** going from `W=1s` to `W=15s+` and flattens
  after — per-tick flush overhead dominates at `W=1s` (15-300×
  more flushes per second than the larger windows). Matches
  the expected shape.
- **RSS trends down with larger `W`** — counter-intuitive if
  you'd expect "longer window holds more state", but consistent
  with DDSketch's per-series summary being bounded regardless
  of observation count. The drop likely reflects GC between
  fewer flush cycles.
- The bandwidth column is only honest for `W=1s` (584.9 B/s)
  and approximately honest for `W=15s` (52.2 B/s). The `60s`
  and `300s` rows are caveat-affected.

## Non-obvious findings worth a second look

1. **Label-axis CPU climb under projection.** If this
   reproduces under v2 methodology, the `AttributeFilter` path
   is hot enough that a ~4× CPU increase for what's notionally
   "just drop a KV" is paper-negative. Action: dedicated
   profile before any further eval runs.
2. **cms-delta memory overhead at 2× cms-full.** Delta
   encoding in sparse-state sketches is a tradeoff, not a win —
   worth an explicit callout in whatever writes up these
   numbers. In-place diff encoding might close this gap.

## Next concrete actions

1. Auto-floor `BYTES_WIN ≥ 2×W` in `run-three-axis-sweep.sh`
   so no one steps on the caveat again. Small driver change.
2. V2 rerun at proper `BYTES_WIN` — ~90 min wall — only if
   absolute bandwidth numbers are needed downstream. The ratios
   above are already informative.
3. Profile the `AttributeFilter` hot path to root-cause the
   label-axis CPU climb.
